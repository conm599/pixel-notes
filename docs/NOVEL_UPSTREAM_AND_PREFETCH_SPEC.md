# 小说服务上游改造与单片机流水线预取规范 (NOVEL_UPSTREAM_AND_PREFETCH_SPEC)

> **版本**：v2.2  
> **适用对象**：上游小说抓取服务开发者、中转层守护进程、MCU / 4G 模组端开发者  
> **核心目标**：彻底消除 720ms 上游抓取瓶颈，实现单片机翻页与预取 **0ms 瞬时响应**。

---

## 一、改造背景与耗时现状拆解

实测单片机通过 4G 模组拉取小说切片的耗时分布：
* **公网往返物理延迟 (RTT)**：~110ms（光速物理极限）；
* **中转层内存命中 (Cache Hit)**：**<1ms**（总耗时约 110ms）；
* **冷请求（首次访问未缓存章节）**：**~870ms**，其中 **720ms 全卡在上游反复爬取番茄官方接口**！

为了彻底抹平这 720ms，需要上下游协同完成以下轻量改造。

---

## 二、上游小说服务期望改造规范（给上游开发者）

### 2.1 痛点与解决原则
1. **禁止按“页”向官方重复爬取**：
   番茄官方给出的原始数据就是整章文本（2000~3000 字）。上游不要替单片机切片，**直接将整章纯文本一次性提供给中转层**，切片由中转层统一执行。
   * **收益**：整章只需爬取 1 次，同章后续 7~10 页全部由中转层内存秒回，避免上游被重复打爆。
2. **轻量内存/临时文件缓存（杜绝存储爆炸）**：
   上游**不需要**使用重型 SQL 永久存储全量小说（避免存储空间不足）。
   上游只需在内存（或 `/tmp/` 目录）维护一个 **LRU 50 章轻量缓存池（或保留 30 分钟）**：
   * 存储占用仅约 **5MB ~ 10MB**，毫无机器压力；
   * 读者阅读当前章节时，所有重复或预取请求直接走上游内存命中，上游处理延迟由 **720ms 降至 2ms**！

### 2.2 上游接口协议期望（TCP 单行模式）

#### 指令格式：
```text
CHAPTER_RAW <KEY> <CHAPTER> <BOOK_ID>\n
```
*(兼容形式：亦可约定 `CHAPTER <KEY> <CHAPTER> 0 <BOOK_ID>\n`，即页码传 0 代表获取整章)*

* **参数**：
  * `KEY`：番茄上游鉴权 Key（如 `5b42436aea8a5296e40b4b95d2ed2ad7`）
  * `CHAPTER`：整数章节号（1, 2, 3...）
  * `BOOK_ID`：番茄书籍 ID（纯数字，如 `7128048920910892067`）

#### 期望上游回包 JSON 格式（单行，`\n` 结尾）：
```json
{
  "title": "第12章 牛顿管不了我们呀",
  "chapter": 12,
  "text": "整章完整纯文本正文（包含所有自然段落，无需分页切片，UTF-8 编码）..."
}
```

* **字段规范**：
  * `title`：章节标题（如 `第12章 ...`）
  * `chapter`：章节号（整数）
  * `text`：该章节全部正文（纯文本，保留换行 `\n`）
  * **不要包含 `page` 和 `pages` 字段**（或留空），中转层收到后会自动计算总页数并按自然段落切片。

## 三、中转层已上线的架构升级（自动对接）

中转层（`tcp_server.php`）已完成以下核心能力部署，无需等待上游即可自适应运行：

### 3.1 整章自然段落智能切片器 (`splitChapterTextIntoPages`)
* 一旦上游返回整章纯文本，中转层自动以自然换行 `\n` 为优先分割边界，将整章精准切片为每页约 270~290 汉字；
* **字节安全红线**：单页切片严格控制在 **<= 850 字节 UTF-8**，为单片机 1024 字节静态缓冲预留充足的 JSON 元数据空间；
* **全章预热**：单次请求拉回整章后，中转层内存 LRU 池立即填满该章所有页（第 1 页到最后一页），后续翻页全部 0ms 返回。

### 3.2 方案 3：跨章临界点静默预读下一章 (已实测上线)
* **机制**：当中转层向单片机返回某章最后 1~2 页（如读到第 1 章第 7/8 页）时，中转层在后台**静默拉取第 2 章第 1 页并写入 LRU 缓存池**；
* **实测数据**：
  ```text
  [读者读第1章末页 P=7] -> 耗时 1675ms（首次冷拉并触发后台预读）
  [读者翻入第2章第1页 P=8] -> 耗时仅 177.8ms（命中静默预读缓存，VPS处理 0ms！）
  ```
* 彻底抹平跨章时的网络卡顿感。

## 四、设备端（单片机 / 4G 模组）并行与预取最佳实践

针对单片机 3×1KB 静态预取队列，推荐采用以下两种高效模式：

### 做法 A：单连接流水线（Pipelining，利用 Keep-Alive）
无需等第 1 页回包才发第 2 页，在已建立的 TCP 连接上**一次性写入 3 行命令**：
```cpp
// 1. 一口气流水线发送 3 行
client.print("NOVEL " + apiKey + " 82\n");
client.print("NOVEL " + apiKey + " 83\n");
client.print("NOVEL " + apiKey + " 84\n");

// 2. 连续读回 3 行独立 JSON，填入 3x1KB 静态队列
for (int i = 0; i < 3; i++) {
    String jsonLine = client.readStringUntil('\n');
    parseAndPushQueue(jsonLine);
}
```

### 做法 B：批量指令 `NOVELS`（代码最简单，推荐）
```cpp
// 一条指令索取 3 页
client.printf("NOVELS %s 82 3\n", API_KEY);

// 循环接收 3 行回包（实测总耗时仅 201ms）
for (int i = 0; i < 3; i++) {
    String jsonLine = client.readStringUntil('\n');
    parseAndPushQueue(jsonLine);
}
```
